### 1.3 `token-spending-limit` compared with `spending-limit` (#405 inputs)

`spending-limit` was hardened in #399. `token-spending-limit` did not receive the
same hardening:

| Guard                                         | `spending-limit`        | `token-spending-limit` |
| --------------------------------------------- | ----------------------- | ---------------------- |
| Bounded contexts per call (`MAX_CONTEXTS`)    | yes (16)                | **no**                 |
| `from == bound wallet` check on `transfer`    | yes (`ContextMismatch`) | **no**                 |
| Test pinning the tumbling 2× across a boundary (M3) | yes               | **no**                 |
| Re-simulation / determinism test              | yes                     | **no**                 |

The missing `from` check is mitigated in practice: the bound token is a SAC, and a
SAC's `transfer` calls `from.require_auth()`, so the wallet is only asked to
authorize transfers from itself. That mitigation depends on the token, not on the
policy. The missing context bound matters because facilitators re-simulate
`__check_auth` repeatedly.

### 1.4 passkey-kit authorization properties that shape these designs

From reading `smart-wallet` at `50981cc`. This is source analysis and has **not
yet been reproduced on-chain**:

- `Signature::Policy` carries no secret. Anyone can submit it, so a standalone
  policy signer's bounds are the only control on what it authorizes.
- **Sole self-removal skips `policy__`** (`is_sole_self_removal`). A standalone
  policy signer can be detached by a transaction that carries only
  `Signature::Policy`. That appears to let **anyone** detach any standalone policy
  signer. This fails safe (authority only shrinks), but it is a griefing and
  denial-of-service vector:
  - for scheduled payments (an attacker can cancel a schedule);
  - for agent keys: detach, then the permissionless `uninstall`, then the agent's
    required co-signer fails `NotInstalled`, and the key is bricked (fails closed).

  To be confirmed on testnet before it is recorded as a finding.
- Policies inside `SignerLimits` run last and deduplicated. Two distinct
  state-committing policies in one required-keys list can leave committed state
  behind after a later rejection. Do not combine them.

### 1.5 Other baseline facts

- `isBlockedAddress` (`services/worker-service/src/repo-url-guard.ts`) still has
  the RA-7 gap: hex-form IPv4-mapped (`::ffff:7f00:1`) and NAT64 (`64:ff9b::/96`)
  addresses are missed. RA-7 is still OPEN.
- Nothing in the repo calls Soroban `getEvents` or retries `txNoAccount` /
  `txBadSeq` / `MissingValue`. Transaction history (#403) is open and has no
  implementation, so the shared-indexer decision is being made fresh.
- The backend has no user identity (`architecture-analysis.md` §5). The only
  capability is the wallet-service session bearer, and RA-3/M1 scoped it narrowly.

## 2. Design plan

### #408: scheduled payments

- A new policy contract, `policy-templates/recurring-payment`, with immutable
  config: wallet, token, recipient, exact amount, interval, start, a mandatory
  `max_executions`, and an optional end time. `policy__` accepts exactly one
  context: `token.transfer(wallet, recipient, amount)`. Everything else fails
  closed.
- **Missed intervals: skip, never catch up.** A period is
  `(now - start) / interval`, and at most one execution is allowed per period
  index. A missed period is lost. The total can never exceed
  `amount × max_executions`. Two executions can land close together across a
  period boundary; that is documented and tested, as M3 is.
- Pause is on-chain (`set_paused`, requires wallet auth). It can only reduce
  authority.
- **Cancel is an on-chain detach** (`remove_signer(Policy)`), signed by the passkey.
- The scheduler lives in `worker-service`. It is a trigger with a fee-paying
  G-account and **no wallet authority**, so compromising it cannot exceed the grant.
  It discovers schedules from the shared indexer's `signer_added` /
  `signer_removed` events.
- Testnet proof: execution inside bounds, an over-bound attempt rejected, and a
  post-cancel attempt rejected, each backed by a real transaction.

### #410: contacts and SEP-2

- Contacts are stored in the browser and keyed by account and network. The server
  gets no personal data, and there is no backend identity to scope them to.
- A server-side SEP-2 resolver:
  - https only;
  - every resolved IP is checked with `isBlockedAddress`, and the connection is
    pinned to the checked IP (DNS-rebinding close);
  - no redirects, a size cap and a timeout;
  - the stellar.toml `FEDERATION_SERVER` is guarded the same way;
  - the response is validated before use.
- `isBlockedAddress` moves to `@vellar/service-kit` and is fixed for RA-7 by
  canonicalizing to bytes.
- The address is re-resolved at send time. The approval screen always shows the
  resolved address beside the label, and flags a mapping that changed.

### #409: shared events indexer

- **One indexer in `worker-service`**, feeding both notifications and transaction
  history (#403).
- It reads Soroban `getEvents` (SAC `transfer`, wallet `signer_added` /
  `signer_removed`), normalizes the events, and writes them with deterministic
  IDs.
- The checkpoint advances only after the events are written, and replay is
  idempotent.
- Retries are bounded, using `@vellar/service-kit` `retryWithBackoff`.
- If the RPC retention window has passed, the gap is recorded durably instead of
  being skipped silently.
- Notifications are in-app only. Reads are account-scoped in the query layer.
